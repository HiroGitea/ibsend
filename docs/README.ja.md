## ibsend を選ぶ理由

| | 機能 | 得られるもの |
|---|---|---|
| ⚡ | **RDMA の直接データパス** | `RDMA_WRITE_WITH_IMM` が登録済みメモリへ直接書き込み、制御とデータは一つの RC キューペアを共有します。 |
| 🧠 | **RAM ステージング** | 自動調整される大きなプールがリンクとディスクの速度差を吸収し、受信側が非同期に排出する間も送信側はリンク速度で完走できます。 |
| 🔁 | **再開と検証** | 中断した `.part` ファイルをバイト単位で再開し、転送ファイルをハードウェア支援の CRC32C で検証します。 |
| 🔄 | **対等なピア** | 発見可能な同じデーモンがファイルやディレクトリツリーを送受信し、任意のドラッグ＆ドロップ GUI も同じコアを使います。 |

### パフォーマンス概要

デュアルポート 40 Gb QDR HCA で **3.47 GB/s（27.8 Gb/s）**を持続しました。
これは符号化後のリンクデータレートの 87% で、PCIe 2.0 x8 の実用上限にも達して
います。書き込み先の ZFS が 831 MB/s でも、RAM ステージングにより送信側は 2 GB
を **0.62 秒**で完了しました。環境と全結果は[実測](#実測)を参照してください。

**クイックナビ：** [クイックスタート](#クイックスタート) ·
[コマンド](#コマンド) · [仕組み](#仕組み) · [実測](#実測) ·
[既知の制限](#既知の制限) · [コントリビューション](../CONTRIBUTING.md)

> **言語について：** CLI と GUI のメッセージは現在中国語のみです。
> ドキュメントは英語・中国語・日本語で提供しています。

## 必要なもの

- IPoIB を設定した InfiniBand または RoCE の HCA。IPoIB はアドレス解決
  （`rdma_resolve_addr` → GID）とサブネット走査にしか使いません。
- `rdma-core`（libibverbs、librdmacm）とそのヘッダ。
- Linux と比較的新しい Rust ツールチェイン。
- メモリをロックする権限（[メモリロック](#メモリロック)を参照）。

## ビルドとインストール

```sh
git clone https://github.com/HiroGitea/ibsend.git
cd ibsend

cargo install --path . --locked                    # CLI のみ
cargo install --path . --locked --features gui     # CLI + GUI
```

GUI を feature の後ろに置いたのは意図的です。ヘッドレスのノードに OpenGL の
依存関係一式を背負わせる理由はありません。

開発ビルドでは `cargo install --path . --locked` の代わりに `cargo build` を
使えます。インストール後は `$HOME/.cargo/bin` が `PATH` に含まれることを確認して
ください。

## クイックスタート

```sh
# 各ノードで常駐させる。発見可能かつ受信可能な状態になります
ibsend daemon --out /data

# ファブリック上に誰がいるか見る
ibsend discover

# ファイルでもディレクトリでも、アドレスでもデバイス名でも指定できます
ibsend send 10.0.0.1 ./big.iso
ibsend send nas ./photos
```

ディレクトリは相対パスを保ったまま再帰的に展開され、受信側がツリーを再構築
します。シンボリックリンクは辿らずにスキップします。辿るとループを招き、
ツリー外のデータを黙って巻き込み、「結局何を送ったのか」が予測不能になるため
です。

## メモリロック

RDMA の登録は物理ページをピン留めしますが、多くのディストリビューションで
`RLIMIT_MEMLOCK` の既定値は 8 MB です。ステージングプールにはまるで足りず、
そしてこの設計の価値の大半はそのプールにあります。

より影響範囲の狭い解決策は、このバイナリだけに `CAP_IPC_LOCK` を与えることです。
カーネルの `ib_umem_get` での判定は「上限超過**かつ** CAP_IPC_LOCK なし」なので、
この capability があれば上限そのものを緩めずに済み、ユーザーが動かす他の
プロセスは従来どおりの制限下に留まります。

`ibsend authorize` は環境に応じて手段を選びます。

| 環境 | 手段 |
|---|---|
| デスクトップ（`DISPLAY`/`WAYLAND_DISPLAY`） | polkit のダイアログ、または GUI の認可ボタン |
| SSH・ヘッドレスだが端末あり | `sudo` を呼び、その場でパスワードを尋ねる |
| スクリプト、端末なし | `sudo setcap …` を表示して手動実行を促す |

利用可能なプールが既に十分な大きさなら何も言いません。十分なプールをさらに
大きくするためだけにパスワードを求める理由はないからです。

知っておくべき点が三つあります。

- **capability はバイナリの拡張属性に書かれます。** 実行ごとの昇格ではないので、
  一度付与すると誰がそのファイルを実行しても付いてきます。
- **ファイル capability は `execve` 時に読み込まれます。** 付与したプロセス自身は
  使えず、再起動が必要です。GUI は自分で再起動します。
- 再ビルドするとファイルが置き換わり、capability は消えます。

パッケージではインストール後フックで行うべきです。

```sh
setcap cap_ipc_lock+ep /usr/bin/ibsend
```

## コマンド

| コマンド | 用途 |
|---|---|
| `ibsend daemon` | 常駐。発見可能かつ受信可能 |
| `ibsend discover` | IPoIB サブネットを走査してピアを探す |
| `ibsend send <ピア> <パス…>` | ファイルまたはディレクトリを送る |
| `ibsend recv` | 一度受信して終了 |
| `ibsend authorize` | メモリロック権限を要求する |
| `ibsend-gui [ファイル…]` | GUI（ドラッグ＆ドロップ、Ctrl+S で送信） |

`--bind` は既定で最初の IPoIB インターフェイスを使います。プールサイズと
スラブの分割は自動調整され、`--pool`、`--slab`、`--name` で上書きできます。

## ライブラリとして使う

```rust
use ibsend::{Incoming, Receiver, RecvConfig};

let mut rx = Receiver::start(RecvConfig::new("10.0.0.2"))?; // 即座に返る
loop {
    match rx.accept_one(2000)? {          // 登録は待ち時間と重なって進む
        Incoming::Transfer(m) => {
            rx.receive(&m, |p| println!("{} B/s、滞留 {} B", p.rate(), p.staged))?;
            rx.end_session()?;            // プールは保持したまま次のピアへ
        }
        Incoming::Dropped(why) => eprintln!("破棄：{why}"),
        _ => {}
    }
}
```

モジュール構成は `proto`（ワイヤ形式）、`tune`（自動調整）、`walk`（ディレクトリ
展開とパスの無害化）、`discover`、`recv`、`send`、`daemon`、`authorize`、`crc`。
`ffi` は非公開です。CLI は引数解析と進捗表示しかしません。

## 仕組み

**チャンク番号はワイヤに乗りません。** RC キューペアは順序を保つので、受信側は
到着数を数えるだけで済みます。32 ビットの immediate はすべてそのチャンクの
バイト数に使われます。これならバイト単位で正確で、かつ総量が事前に分からない
ストリーミングにも対応できます。`imm == 0` がストリームの終わりです。

**接続してから交渉し、最後に登録する。** 制御プレーンをキューペアに載せると
順序が自然に整います。QP を確立し、その上で分割方法を決め、それから両側が
プールを登録します。制御プレーンが TCP だった頃はこれを逆順にせざるを得ず、
プール情報を `rdma_cm` の `private_data` に押し込む必要がありました。

**クレジットウィンドウはプール全体です。** 受信側は排出しながら「解放したスラブ
数」を返し、送信側はその範囲内でのみ書き込みます。したがってデータは送信側を
絞る代わりに RAM に積み上がり、プールが本当に埋まるまで待たされません。

**一度登録し、何度も使う。** セッションの終了ではキューペアだけを破棄し、登録済み
プールは保持します。デーモンは起動時に一度だけ登録コストを払えば済みます。
プールをどうスラブに切るかは純粋な算術なので、転送ごとに無料で決め直せます。

**登録は非同期です。** 確保、ページのプリフォールト、`ibv_reg_mr` はバックグラウンド
スレッドで走り、ピアを待つ時間と重なるため、起動時に体感できる停止がありません。

**2 MB のヒュージページ。** プールは 2 MB 境界に整列し `MADV_HUGEPAGE` を付けます。
古い世代の HCA はアドレス変換キャッシュが小さく、16 GB を 4 KB ページで扱うと
400 万エントリ必要になりますが、ヒュージページなら 512 分の 1 で済みます。

**両側に I/O スレッドが一つずつ。** 送信側は読み出しスレッド、受信側は書き込み
スレッドを持ち、メインスレッドはキューペアの操作しかしません。libibverbs が
スレッドセーフでないためです。`ibx_recv_wake` だけが例外で、eventfd に 8 バイト
書くだけで verbs オブジェクトには一切触れません。

## 設計上の覚え書き

自明でなかったことを、二度と同じ回り道をしないために残しておきます。

**受信ワークリクエストはメッセージ種別に関係なく投入順に消費されます。** 一つの
キューでバッファサイズを混在させると、大きなメッセージが小さなスロットに落ちて
`local length error` になります。そのため受信スロットはすべて同じサイズにし、
メッセージ種別はフレームヘッダのフラグで区別しています。

**戻り値の空間を絶対に重ねないこと。** `poll_cq` 系の関数は「完了をいくつ処理したか」
を返しますが、小さな正の数に「タイムアウト」の意味も持たせると、たまたまその数だけ
完了がまとめて来た回がタイムアウトと誤読されます。これが間欠的なハンドシェイク
ハングの原因でした。

**バックグラウンドスレッドの完了をタイムアウトで「気づく」設計にしないこと。**
書き込みスレッドの完了は、受信待ちでブロックしているメインループからは見えません。
クレジットの返却がタイムアウトまで遅れ、ウィンドウが狭いとチャンクごとに
1 タイムアウト分の往復に退化します。eventfd で起こすのが正解です。

**プリフェッチの深さは両側のウィンドウに従うこと。** ローカルのスラブ数だけを見て
先読みすると、相手のクレジットウィンドウがより小さい場合にデッドロックします。
先読みがウィンドウを埋める → クレジット待ち → クレジットにはデータ到着が必要 →
データにはコミットが必要 → そのコミットは先読みループの後ろにある、という循環です。

**再試行して良い失敗と、してはいけない失敗を区別すること。** 相手がまだ準備できて
いないための接続失敗は再試行の価値がありますが、ローカルの資源不足によるものは
決してそうではありません。区別しないと、本来即座に明示されるはずのエラーが数分間の
無言のハングに化けます。

**すべてのタイムアウトには存在理由があります。** 相互待ちを防ぐもの、半死の送信側が
デーモンを永久に塞ぐのを防ぐもの、そして接続だけして何も言わないピアを捕まえる
アイドルタイムアウトです。

**接続を破棄するときは必ず理由を添えること。** ハンドシェイクのエラーを黙って
飲み込むと、「相手は接続したのに何も起きない」という誰にも診断できない状況になります。

**マジックとバージョンは分けて持つこと。** 配布すればバージョンの食い違いは必ず
起きます。今はどちらの側もミリ秒単位で「プロトコルバージョン不一致：相手 vN、
自分 vM」と報告します。片方が黙って切断し、もう片方がタイムアウトまで待つ、という
ことはもうありません。

**glibc のシンボル混入に注意。** ローリングリリースでビルドすると、安定版で起動
しないバイナリが黙って出来上がることがあります。`atoi` は `__isoc23_strtol`
（2.38）を、`std::process::Command` は `pidfd_spawnp`（2.39）を引き込みます。
CLI はどちらも避けており、glibc 2.34 より新しいものを必要としません。

## 実測

2 台のホスト、デュアルポート 40 Gb QDR の HCA、IPoIB は connected モードで
MTU 65520、PCIe 2.0 x8。送信側はローリングリリースの Linux、受信側は Debian 12。

**リンクの上限**（転送量がプールより小さく、フロー制御が働かない条件）：

| 送信側の在飛スラブ数 | 速度 |
|---|---|
| 6 × 1 MB | **3.47 GB/s** |
| 3 × 2 MB | **3.47 GB/s** |
| 1 × 4 MB | 1.94 GB/s |

3.47 GB/s は 27.8 Gb/s で、8b/10b 符号化を差し引いた QDR のデータレート
32 Gb/s の 87 %。同時に PCIe 2.0 x8 の実用上限にもちょうど当たっており、
二つの制限が偶然同じ数字に落ちています。

最後の行はパイプライン化が必須であることを示しています。スラブが一つだけだと
送信側は各書き込みの完了を待ってからでないと再充填できず、読み出しと送信が
直列化してピークの 56 % まで落ちます。

**RAM ステージングの効果**（2 GB を ZFS プールへ、ステージングプール 1.5 GB）：

| | 所要時間 | 速度 |
|---|---|---|
| 送信側 | **0.62 秒** | 3.48 GB/s |
| 受信側（書き込み込み） | 2.58 秒 | 831 MB/s |
| RAM 滞留のピーク | | 481 MB |

ディスクは 831 MB/s しか飲み込めませんが、送信側は 0.62 秒で完了しました。
この 4.2 倍の差をプールが吸収しています。ステージングがなければ送信側はディスク
速度まで絞られ、同じく 2.58 秒待つことになります。

フロー制御が働く様子は直接観測できます。滞留量が 1.07 GB のプールに対して
839 MB から 975 MB へ増えるのと同時に、速度は 3.49 GB/s から 2.60 GB/s へ
下がりました。

すべての転送で SHA-256 が一致し、CRC32C の検証もすべて通っています。

## 中断からの再開

同じコマンドをもう一度実行するだけです。受信側は宛先を走査し、正しいサイズで
既に存在するファイルは丸ごとスキップ、`.part` があればその長さから再開、
それ以外は最初から送ります。つまり `.part` は掃除すべきゴミではなく、再開点
そのものです。

スキップはファイル単位（サイズ一致を完全とみなす）、再開はバイト単位です。

## チェックサム

データが流れ切った後、送信側がファイルごとの CRC32C を制御チャネルで送り、
受信側が突き合わせます。受信側はどのみちディスクを待っている書き込みスレッド上で
計算します。SSE4.2 の `crc32` 命令はおよそ 8 GB/s 出るため
（`cargo run --release --example crcbench` で測れます）、リンクより十分に速いです。

これが何を捕まえるのかを明確にしておきます。**リンクの完全性は既にハードウェアが
担保しています。** IB のパケットはすべて HCA が検査する ICRC と VCRC を持ち、RC は
ハードウェアで再送するので、ワイヤ上の破損はソフトウェアのチェックサムが見つけ
られるようなものではありません。捕まえるのはこのプログラム自身のバグ、非 ECC
メモリのビット反転、ディスクの書き込みエラーです。この種類は古い HCA には
オフロードできません。署名や T10-DIF のオフロードは後の世代の機能だからです。

**再開したファイルは、今回送ったバイト範囲だけが検証されます。** 既存部分を読み
直す費用は再送とほぼ変わらず、それでは再開する意味がなくなります。出力で明示
します。

## 既知の制限

- 空のディレクトリは転送されません（ファイルのみ）。
- 暗号化も認証もありません。IB サブネットは信頼できるプライベートネットワークで
  あることを前提としています。なお RDMA のトラフィックは `iptables` でも
  フィルタできません。そのアクセス制御は rkey、パーティションキー、サブネット
  マネージャ側にあります。
- スキップ判定はファイルサイズのみを比較し、内容は見ません。
